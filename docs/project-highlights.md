# 候选项目亮点与性能记录

## 1. 图片引用校验：逐图 RPC 改为内部批量查询

记录日期：2026-10-25。状态：代码与回归测试已完成；本机 HTTP 微基准已实测；真实 PostgreSQL/部署环境端到端性能尚未测试。

这个可以作为一个有业务背景、可解释、可验证的性能优化点。亮点不是“多写了一个接口”，而是识别了调用粒度不匹配，减少远程往返和过量数据读取，并保留权限、完整性与事务边界。

### 背景与实现

原来 History 的 `replaceVisuals` 每张图片调用两次公开 GET：查询图片，再查询当前用户/Assessment 的标注集。最多 12 张时是 24 次串行 HTTP 请求；公开响应还携带该业务不需要的签名 URL、图形等字段。

现在改为一次 `POST /internal/image/visual-references/resolve`，请求包含 Assessment 和完整图片 ID 列表，显式传递可信 `X-User-Id`。Image 在同一可重复读快照中做两次批量 SELECT，只返回 `pictureId/sourceType/annotationSetId`：

1. 批量查未删除且当前用户可访问的图片，逐项确认全部存在且为 AVAILABLE；公共标准图允许共用。
2. 批量查当前用户、当前 Assessment 的标注集；没有标注允许返回 null。
3. 按请求顺序返回，任何图片非法都整批失败，不静默丢弃。
4. History 校验批量响应的完整性后，再开启本地短事务 CAS 更新 Assessment 并替换关联；没有把网络调用放进写事务。

前端公开接口、数据库结构和原单图 GET 均保留。空图片列表在 History 为 0 次 RPC，Image 直接收到空列表时也为 0 次查询。

| 图片数 | 原 HTTP 次数 | 新 HTTP 次数 | 次数减少 |
| --- | --- | --- | --- |
| 1 | 2 | 1 | 50.00% |
| 6 | 12 | 1 | 91.67% |
| 12 | 24 | 1 | 95.83% |

“12 张图减少 95.83% 的远程调用次数”是次数指标，不等于“整个系统性能提高 95.83%”。

### 实测范围与环境

- 完成时间（UTC）：`2026-10-25T02:16:58.625883400Z`，即北京时间 2026-10-25 10:16:58。
- 系统：Windows 11 10.0 / amd64；CPU 环境标识 Intel64 Family 6 Model 183 Stepping 1；JVM 可用逻辑处理器 24。
- JVM：Java HotSpot(TM) 64-Bit Server VM 21.0.6；Spring Boot 4.0.6，现有 Spring Cloud OpenFeign 客户端。
- 真实生产 `ImageClient` Bean → `127.0.0.1` 上随机端口的 JDK HttpServer 测试替身。HTTP 编解码和调用耗时真实发生，但服务端不是运行中的 Image Controller/SQL。
- 本机 Docker 引擎未运行。本轮不包含真实 PostgreSQL、MinIO、Nacos、Gateway、TLS、History 写库、手机网络和并发负载。
- Wi-Fi/热点的 2.4GHz、5GHz 不在本次回环调用链路中；不要为了复跑本测试切换热点。
- 单线程；1/6/12 张图；每组 5 对预热，25 对正式样本，轮流采用“旧→新”和“新→旧”顺序，共 300 个正式操作样本。
- 计时使用 `System.nanoTime`，包围整个客户端校验阶段，包含同步 HTTP、JSON 解码及校验断言；不含 Spring 启动和预热。P50/P95 使用 nearest-rank。
- 统一让旧、新响应都发送 `Connection: close`，降低本机 keep-alive delayed ACK 对结果的干扰；因此不模拟生产连接池复用。
- 固定所有图片可用、所有标注集存在。原公开响应模拟完整元数据、URL 字符串和一个圆圈；批量响应仅包含引用字段。图片二进制没有传输，URL 没有真实签名计算。
- 这是单次运行的受控 HTTP 微基准，不是 JMH、生产压测或整条 `replaceVisuals` 的延迟承诺；JIT、调度和 GC 会影响复跑结果。

| 图片数 | HTTP 次数：旧 → 新 | 平均 ms：旧 / 新 | P50 ms：旧 / 新 | P95 ms：旧 / 新 |
| --- | --- | --- | --- | --- |
| 1 | 2 → 1 | 2.816 / 1.664 | 2.901 / 1.661 | 3.422 / 2.071 |
| 6 | 12 → 1 | 10.408 / 1.214 | 10.597 / 1.233 | 12.099 / 1.532 |

12 张图这一次的客户端校验阶段平均耗时为 **19.446 → 1.131 ms**，P95 为 **27.683 → 1.370 ms**。这些是上述本机替身环境的实测值，不能写成生产接口 SLO 或真实数据库端到端收益。

### B. 敏感性试验：每请求人工等待至少 5ms

下面仍为实际测到的耗时，但“额外成本”由服务端 `parkNanos` 人为注入，不是公网、热点或真实数据库延迟。

| 图片数 | HTTP 次数：旧 → 新 | 平均 ms：旧 / 新 | P50 ms：旧 / 新 | P95 ms：旧 / 新 |
| --- | --- | --- | --- | --- |
| 1 | 2 → 1 | 31.129 / 15.568 | 31.204 / 15.537 | 31.863 / 16.468 |
| 6 | 12 → 1 | 186.319 / 15.586 | 186.286 / 15.516 | 187.589 / 16.155 |
| 12 | 24 → 1 | 373.164 / 15.625 | 372.903 / 15.573 | 375.675 / 16.457 |

本机 Windows 调度会使 5ms 等待超时返回；本次单个批量请求均值约 15.6ms，不能声称这是精确的“网络 RTT=5ms”实验。该组仅说明请求级固定开销会随串行请求数累加，不应单独拿来宣传生产提升倍数。

### 数据库查询次数：实现分析与测试验证，不是数据库耗时实测

原路径在标注集存在时，每图的 `getPicture` 查询 asset、thumbnail 两次，`getPictureAnnotationSet` 查询 asset、annotation_set、shapes 三次，合计 **5N**。无标注集时后者少一次 shapes 查询，合计 **4N**。这来自代码路径推导，未连接真实数据库采样 SQL 日志。

新批量成功路径固定 **2 次** Mapper SELECT（只投影必要字段），无论图片数量多少；空列表 0 次，图片校验失败提前结束为 1 次。新路径的次数已由 Service 测试的 Mapper 调用断言验证，但没有测量真实数据库 IO 时间。

例如 12 张且都有标注时，查询路径是 60 → 2；这个数字不能冒充真实 PostgreSQL 性能提升比例。

### 简历/面试候选表述

> 针对评估图片关联中的逐图远程查询，设计内部批量解析接口，将 12 张图片的校验从 24 次 RPC 收敛为 1 次，并通过两次批量 SQL 完成图片与标注引用解析；保留用户归属、状态校验与本地乐观锁事务边界，编写可复现 Feign/HTTP 微基准验证请求数、时延和 JSON 体积变化。

如果要加耗时，只能附带“本机 HTTP 测试替身、无额外等待、25 对样本”等口径；当前不能写生产 QPS、真实数据库耗时或全链路提升倍数。该接口没有增加服务身份认证，不能将 `/internal` 命名本身描述成安全隔离方案；现有 Gateway 不路由该路径，部署仍需限制服务端口访问。
